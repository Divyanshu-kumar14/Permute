## 3. The one place the PRD and the vendor text disagree

The vendor's *Priority inheritance and messages* page says a receive from a **lower**-priority sender lowers the server's priority to that sender's. Its own example has a server configured at 22 serving a 10-priority client and says "the change … takes place when the server receives the message".

PRD 9.1 defines:

```
eff(t) = max(base_prio, sticky_prio, mutex_boost, max(prot_ceil …))
```

With that formula the effective priority cannot fall below base. The two statements cannot both hold.

**Resolution:** follow the PRD. The inherited value is still *assigned* (a receive from a 10-priority client sets `sticky_prio` to 10, observable and traceable), but `eff_prio` stays at the server's 22. The PRD is normative, and the difference only appears when a receiver's own priority exceeds its clients' — not a configuration any of C12/C13 exercises. Recorded as IMP-20 and `LIMITS.md` divergence #11, with a test (`test_receive_assignment_never_drops_below_base`) that pins the chosen behaviour so it cannot drift silently.

This is the kind of thing worth surfacing rather than quietly choosing: it changes scheduling order in a real deployment, and a reviewer should be able to disagree with the call.

## 4. Mutex inheritance is transitive, because the vendor text says so

"its new priority is the maximum of its own priority and the priorities of those threads it still blocks, **either directly or indirectly**."

So blocking on a mutex does not just boost the direct owner; `boost_chain` walks up the wait chain, applying the waiter's priority to every owner it reaches, with a depth bound of the thread count to make a cycle harmless. The test builds C (5) ← B (10) ← A (30) and asserts both B and C reach 30. Unlock recomputes from the waiters that remain, which is what makes the boost revert rather than decay.

The boost is derived from the mutex table on every recompute rather than maintained incrementally. A donor list can drift from the waiters that justify it; a scan of 128 mutexes on unlock cannot.

## 5. Boundary

| In scope | Out of scope |
|---|---|
| Both inheritance mechanisms and their reverting rules | Wiring priority changes into preemption decisions (needs the executor) |
| Receive-time assignment on messages and pulses | `pthread_mutex_*` ABI wrappers (later shim task) |
| Mutex lock/unlock/handoff semantics | Robust mutexes; a dead owner leaves the mutex locked, which is the honest deadlock a later oracle should report |

A thread that dies holding a mutex leaves it held and its waiters blocked. That is QNX's behaviour for an ordinary (non-robust) mutex, and it is exactly the `deadlock` outcome the oracle tier exists to detect. Silently releasing it would hide a real defect class.
